# /brainstorm — 설계 정제 (Phase 0.5)

요구사항이 굳기 전에 **소크라테스식 질문으로 문제를 정제**하고, 대안을 비교해
설계 문서를 만든다. 산출물은 spec-writer 브리프의 입력이 된다.

## 사용법
```
/brainstorm 알림 시스템을 어떻게 만들지 고민 중
/brainstorm                # 주제를 대화로 파악
```

## Process

### 1. 현재 상태 파악 (질문 전에 먼저 조사)
- 관련 코드·문서(SPEC.md, ARCHITECTURE.md, feature_list.json) 읽기
- 기존 유사 기능, 재사용 가능한 컴포넌트 식별
- 조사 없이 질문부터 시작하지 않는다 — 질문의 질은 컨텍스트에서 나온다

### 2. 소크라테스식 인터뷰 — AskUserQuestion으로 **한 번에 하나씩**
질문을 몰아서 던지지 않는다. 답이 다음 질문을 결정한다. 탐색 축:
- **목적**: 이걸로 해결하려는 실제 문제는? 누가 쓰는가?
- **제약**: 기존 시스템·기술 스택·일정·규정의 제약은?
- **실패 모드**: 이게 잘못되면 어떤 모습인가? 최악의 시나리오는?
- **범위**: 첫 버전에서 빼도 되는 것은? (YAGNI 압박)
- **보안/데이터**: 다루는 데이터의 민감도는? (security_tier 사전 판단)

### 3. 대안 제시 — 최소 2개
- 각 대안의 트레이드오프를 표로 (복잡도, 위험, 확장성, 구현 비용)
- **권장안을 명시**하되 근거를 함께 — 나열만 하고 떠넘기지 않는다
- AskUserQuestion의 preview로 구조 비교 제시 가능

### 4. 점진 검증
- 설계를 섹션별로 요약 제시 → 사용자 동의 확인 → 다음 섹션
- 한 번에 전체 설계를 쏟아내고 "어때요?" 하지 않는다

### 5. 산출물 저장 — `docs/brainstorms/{YYYY-MM-DD}-{slug}.md`
```markdown
# {주제}
## 문제 정의        ← 인터뷰로 정제된 실제 문제
## 결정 사항        ← 선택한 방향 + 근거
## 검토한 대안      ← 기각된 대안과 기각 사유 (재논의 방지)
## 제약·가정
## 보안 고려사항    ← 예상 security_tier, 민감 데이터
## 미해결 질문      ← 스펙 단계로 넘길 항목
```
- 동일 주제의 기존 brainstorm 문서가 있으면 새로 만들지 말고 이어쓰기를 제안
- docs/brainstorms/ 디렉토리가 없으면 생성

### 6. 출구 — 다음 단계 연결
설계가 정리되면 사용자에게 제안:
- 기능화 진행 → `/change-request {정제된 설명}` (brainstorm 문서가 spec-writer 브리프의 핵심 입력)
- 스펙 단계 진행 → 메인 루프 인터뷰는 brainstorm에서 이미 수집된 답을 재사용 — 같은 질문을 반복하지 않는다
- 보류 → 문서만 저장하고 종료

## Constraints
- 코드 작성 금지, 산출물 파일(brainstorm 문서) 외 수정 금지
- 질문은 한 번에 하나 — 사용자가 빨리 진행하길 원하면 축약하되 목적·실패 모드는 생략하지 않는다
- 사용자의 첫 아이디어를 그대로 받아 적지 않는다 — 더 단순한 대안을 최소 하나 검토
