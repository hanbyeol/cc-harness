# /debug — 체계적 디버깅 (근본 원인 우선)

증상 패치가 아니라 **근본 원인을 찾아 최소로 수정**하는 4단계 디버깅 워크플로우.

## 사용법
```
/debug 로그인 후 가끔 401이 떠요
/debug F4: 결제 webhook이 중복 처리됨
```

## /hotfix와의 구분
| 상황 | 사용 |
|------|------|
| 원인이 이미 명확 (오타, 명백한 로직 오류) | `/hotfix` 직행 |
| 원인 불명확, 간헐적, "왜?"를 모름 | `/debug` → 원인 규명 후 수정 |

## 실행 모드 — 단일(직렬) vs 독립 실패 병렬
디버그를 시작하기 전에 실패의 구조를 본다:
- **독립 실패 병렬 모드**: 서로 **독립적인**(다른 파일·서브시스템, 공유 상태 없음) 실패가
  **2개 이상**이고 git worktree가 가능하면, 각 실패를 `isolation: "worktree"` 서브에이전트로
  **병렬 진단**한다(superpowers dispatching-parallel-agents). 각 자식은 **격리 컨텍스트**(세션
  이력 미상속, 부모가 그 실패의 증상·범위만 전달)로 아래 4단계를 독립 수행.
  - **병합**: (1)각 서브에이전트 요약 검토 (2)충돌 확인(같은 파일 수정 → 독립성 오판, 직렬 재실행)
    (3)전체 테스트 실행으로 통합 회귀 없음 확인.
- **단일(직렬) 폴백**: 실패가 **연관**되어 있거나, 시스템 전체 이해가 필요하거나, 원인이
  전혀 안 잡히는 **탐색적** 디버깅이거나, 단일 실패이거나, worktree 미지원이면 직렬로 한다.
  (탐색적·연관 실패를 병렬로 쪼개면 전체 그림을 놓친다)
- **위임 상한**: 병렬 조건을 만족해도 아래는 위임하지 않는다 — (a)직접 소수의 tool call로 끝낼 진단,
  (b)한 실패를 잘게 쪼갠 병렬, (c)자기 진단 결과를 재확인할 목적의 위임. 동시 스폰 수는 필요한 최소로.
  - **(c)의 예외**: 워크플로우가 규정한 **독립 evaluator 판정**과 **F37 critical 2차 판정**은 모델의
    자기검증이 아니라 조직적 통제(INV-1)이므로 예외다 — 위임 상한을 게이트 생략의 근거로 오독하지 않는다.

두 모드 모두 각 (서브)에이전트 내부에서는 아래 4단계를 동일하게 따른다.

## Process

### Phase 1. 재현 고정 (Reproduce)
- 실패를 **결정적으로 재현하는 최소 케이스**를 만든다 — 가능하면 실패하는 테스트로
- 재현 조건 기록: 입력, 환경, 타이밍, 빈도 (간헐적이면 발생 조건 좁히기)
- **재현 없이 다음 단계로 가지 않는다** — 재현 불가 시: 시도한 방법·로그·가설 목록을 정리해
  사용자에게 추가 정보(로그, 발생 시점, 환경)를 요청하고 종료

### Phase 2. 근본 원인 추적 (Root Cause)
- 증상 지점에서 시작해 **호출 체인을 역추적** — 에러가 발생한 곳이 아니라 잘못된 값이 만들어진 곳을 찾는다
- 가설 → 검증 루프:
  1. 가설을 명시적으로 기록 ("토큰 갱신 경쟁 조건일 것")
  2. 가설을 **실행으로만** 검증/기각 (로그 추가, 단정 삽입, 조건 재현 — 추측으로 기각 금지)
  3. 기각되면 다음 가설로
- **가설 3회 연속 기각 시**: 중단하고 가설 목록 + 수집한 증거를 사용자에게 보고 (무한 루프 방지)
- 발견한 원인은 "왜 이 코드가 이렇게 동작했나"까지 설명 가능해야 한다

### Phase 3. 최소 수정 (Minimal Fix)
- **근본 원인 지점만** 수정 — 증상 지점에 방어 코드를 덧대지 않는다
  - ❌ null이 내려오니 호출부에 `if (x != null)` 추가
  - ✅ null을 만들어내는 지점을 수정
- 같은 원인의 다른 발현 지점이 있는지 확인 (동일 패턴 검색)
- 수정 범위가 3파일 이하면 /hotfix의 경량 절차(인라인 contract, 경량 검증) 재사용,
  초과하거나 security_tier: critical 보안 로직이면 `/implement` 절차로 전환

### Phase 4. 회귀 테스트 (Lock It Down)
- Phase 1의 재현 케이스를 **영구 회귀 테스트로 승격** — 같은 버그의 재발을 기계적으로 차단
- 재현 테스트 + 변경 범위 테스트 + (가능하면) 전체 테스트 통과 확인
- progress/lessons.md에 원인 패턴 1줄 기록 (implementer가 다음 iteration에서 참조)

## Output (선택 — 복잡한 디버깅이었던 경우)
```json
// progress/agent-comms/debug-{timestamp}.json
{
  "symptom": "로그인 후 간헐적 401",
  "root_cause": "refresh token 갱신 시 이전 토큰 즉시 무효화 → 동시 요청 경쟁",
  "hypotheses_rejected": ["토큰 만료 시간 오설정", "시계 드리프트"],
  "fix": "grace period 30s 도입 (auth/refresh.go)",
  "regression_test": "auth/refresh_test.go::TestConcurrentRefresh"
}
```

## Constraints
- **원인을 모르는 채 수정하지 않는다** — "이렇게 하니 안 나던데요"는 수정이 아니라 은폐
- 디버깅 중 발견한 무관한 이슈는 수정하지 말고 기록만 (범위 유지)
- firewall이 ask/deny하는 명령(git reset --hard 등)을 우회하도록 지시하지 않는다
- 수정 후 재현 케이스가 통과하고, 기존 테스트가 깨지지 않았음을 실행으로 확인 (evidence)
